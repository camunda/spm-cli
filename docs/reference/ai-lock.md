# `ai.lock` Lockfile

`ai.lock` is **generated by spm and committed** to your repo. It pins every
version selector from [`ai.json`](/reference/ai-json) to an immutable commit SHA,
giving you **reproducible installs**: everyone who runs `spm install` from the
same `ai.lock` gets exactly the same skill content.

## How it relates to `ai.json`

```
ai.json ──resolve──▶ ai.lock ──fetch/project──▶ materialized skills
```

- `ai.json` says *what* you want (e.g. `"branch": "main"` or `"tag": "v1.2.0"`).
- `ai.lock` records *exactly which commit* that resolved to.

| `ai.json` selector | pinned in `ai.lock` as |
|--------------------|------------------------|
| `tag`              | resolved commit SHA    |
| `branch`           | resolved commit SHA    |
| `commit`           | itself                 |
| `version`          | resolved tag + its commit SHA |

A `version` entry stores the requirement in `reference` and the concrete tag it
resolved to in `resolved_tag`:

```json
"linter": {
  "git": "https://github.com/org/linter",
  "reference": "version:^1.2",
  "resolved_tag": "v1.4.1",
  "commit": "<40-hex sha>",
  "store": "linter-1a2b3c4d@<40-hex sha>"
}
```

spm validates it on load: `resolved_tag` must be a semver tag that satisfies the
requirement, and no other selector may carry one.

[Full plugins](/reference/ai-json#plugins) declared under `plugins` are pinned
the same way, and `ai.lock` additionally records each plugin's **bundled skill
set** so `spm status` can tell the materialized plugin skills apart from stale
leftovers.

## Transitive skills

When [`resolveTransitive`](/reference/ai-json#resolvetransitive) is enabled, the
skills discovered in dependencies' nested `ai.json` files are pinned into the
**same flat `skills` map**. Each such entry carries a `requested_by` list naming
the direct dependency(ies) that pulled it in (sorted and deduplicated so the
committed lockfile stays stable). A directly-declared skill omits the field. See
[Transitive Skill Dependencies](/guide/transitive-dependencies).

When two edges request the same skill by **different** selectors that resolve to
the same commit (say `branch:main` and `tag:v1`), the graph keeps one entry, and
its `also_satisfies` list records the other selector(s). That is the pin
evidence that lets later installs — including `spm install --locked` — check
those edges without a remote lookup. It is rebuilt on every install and omitted
when empty.

## Commit it

Commit **both** `ai.json` and `ai.lock`. Never commit the materialized skills —
spm keeps those gitignored.

```bash
git add ai.json ai.lock
git commit -m "chore: pin skills"
```

## Updating pins

`branch`, `tag` and `version` selectors only move when you ask them to (a
`version` range moves to the newest tag still inside the range):

```bash
spm update            # re-resolve all skills to latest, rewrite ai.lock
spm update reviewer   # re-resolve just one skill
```

Until you run `spm update`, `spm install` always reproduces the exact commits
recorded in `ai.lock` — even for a skill declared as `"branch": "main"`.

## Verifying the lock in CI

Plain `spm install` quietly re-resolves (and rewrites `ai.lock` for) any entry
you added or changed in `ai.json` without updating the lock. In CI, run
`spm install --locked` instead: it never re-resolves and never writes
`ai.lock`, and fails listing every dependency (direct or transitive) that is
missing, changed or stale in the lock. Fix it by running `spm install` locally
and committing `ai.lock`. See [`spm install --locked`](/reference/cli-commands#spm-install-locked).

## Fresh clones

On a fresh clone or a new worktree, `spm install` reads `ai.lock`, repopulates
the [global fetch cache](/guide/how-it-works), and re-materializes the
project-local skills. See [Worktrees & Fresh Clones](/guide/worktrees).
